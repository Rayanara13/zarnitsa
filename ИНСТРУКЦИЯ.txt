1. ПОДГОТОВКА И ПРОВЕРКА НОСИТЕЛЯ
=================================

Целевая база — Astra Linux 1.7, x86_64/SSE2, без требования AVX.
Сборочная база — Qt 5.15.2 и glibc 2.28; требуется glibc >= 2.28.
Для окна нужна работоспособная графическая сессия X11/xcb. Для headless
X не нужен. Более новая glibc не заменяет проверку остальных зависимостей.

Полный офлайн-комплект содержит Qt, плагины и вспомогательные компоненты,
но не заменяет ядро ОС, glibc и базовую систему. libgost, libparsec-base3
и libpdp — системные Astra security/MAC ABI, НЕ включены в runtime;
см. runtime/SYSTEM-LIBRARIES.tsv. Нижний проверенный профиль Astra SE 1.7.6:
libgost >= 2.0.2-5+ci4, libparsec-base3 >= 3.4+ci71, libpdp >= 3.4+ci71.
Версии сборочной базы ci5/3.5+ci19 не требуют обновить рабочую ОС.
На 1.7.6 проверены системный и комплектный Qt, offscreen-окно,
headless API и HTTPS с закреплением сертификата. Проверка не заменяет
приёмку трея Fly и filecap-помощника при реальном МКЦ.
Совместимость редакции Astra, политик защиты, файловой системы и графики
проверяется на вашем рабочем месте. Офлайн-установка не должна требовать apt
или доступа к Интернету; отсутствующий базовый компонент получают штатным
согласованным офлайн-способом, а не отключением проверки.

Имя tar-архива:
  Zarnitsa_1.0.0_offline_astra1.7_x86_64_<REVISION>.tar.gz
Имя отдельного пакета:
  Zarnitsa_1.0.0_offline_astra1.7_x86_64_<REVISION>.deb
<REVISION> — фактическая ревизия, а не текст для буквального ввода в shell.

Порядок действий:
  1) Получите комплект из доверенного канала или с проверенного носителя.
  2) Сверьте подлинность происхождения способом, принятым в организации.
     Если отдельно передана доверенная сумма архива, сверьте её до распаковки.
  3) Распакуйте архив обычным пользователем в НОВЫЙ ПУСТОЙ каталог.
     Не накладывайте новый комплект поверх старого. Корень архива — Zarnitsa/.
  4) Перейдите в полученный Zarnitsa/ и проверьте файлы:

       sha256sum --check SHA256SUMS

  5) Убедившись в доверии к комплекту, проверьте runtime:

       ./check-runtime.sh
       ./diagnose.sh

SHA256SUMS подтверждает целостность относительно списка сумм, НЕ подлинность
автора: можно подменить и файлы, и список. Встроенные проверки установщика
не превращают недоверенный архив в доверенный.

Скрипты, ELF-загрузчик, Qt-библиотеки и плагины — исполняемый код. Даже --help,
ldd/check-runtime и diagnose не используйте как «песочницу» для неизвестного
комплекта. НЕЛЬЗЯ вслепую выполнять sudo ./install.sh с чужого носителя.


2. ЗАПУСК БЕЗ УСТАНОВКИ И ВЫБОР QT
==================================

Обычный запуск, в том числе с USB:

  ./zarnitsa.sh

Первые адреса можно передать сразу:

  ./zarnitsa.sh 127.0.0.1 10.10.20.1 10.10.20.10:443 sip:10.10.20.20

Без установки программа по умолчанию хранит конфиг и журнал в HOME,
а не на флешке. Для отдельного рабочего профиля вне комплекта:

  ./zarnitsa.sh --config "$HOME/zarnitsa-work/zarnitsa.json"

Родительский каталог для конфига создаётся при сохранении. Учётная запись
должна иметь право записи; read-only носитель для такого конфига не подойдёт.

Режим Qt по умолчанию — auto:
  - сначала совместимый системный Qt 5.15.x;
  - если проверка не проходит — bundled Qt из runtime/;
  - если не подходит ни один — launcher сообщает ошибку, а не ставит пакеты.

  ./zarnitsa.sh --qt-runtime auto
  ./zarnitsa.sh --qt-runtime system
  ./zarnitsa.sh --qt-runtime bundled
  ZARNITSA_QT_RUNTIME=bundled ./zarnitsa.sh

--qt-runtime имеет приоритет над переменной окружения.
Принудительные system/bundled не делают автоматического перехода на другой
режим. Системный Qt 5.11 не является подходящей заменой Qt 5.15.

Launcher задаёт пути выбранных библиотек и плагинов для своего процесса,
не меняет системные настройки Qt и НЕ меняет текущий каталог. Относительные
--config, --list, --screenshot отсчитываются от каталога, из которого вы
вызвали команду, даже если launcher запущен по абсолютному пути или ссылке.

Флешка с noexec, неподходящими правами или файловой системой может запретить
исполнение bin/zarnitsa. Запуск «bash ./zarnitsa.sh» запрет бинарника не
устраняет. Перенесите ВЕСЬ каталог на разрешённую исполняемую файловую систему.
Не отключайте защиту и не меняйте параметры монтирования без разрешения.

Демонстрация без опроса сети:

  ./zarnitsa.sh --demo
  ./zarnitsa.sh --demo --screenshot ./demo.png --size 1440x900

При --screenshot без DISPLAY launcher выбирает offscreen. Обычный запуск
без DISPLAY не превращается в скрытое окно: для сервера используйте headless.
Демо-данные, включая предысторию и аварии, синтетические.


3. УСТАНОВКА TAR ИЛИ .DEB
========================

Выберите ОДИН способ. Не смешивайте tar и .deb: у них разный код, но имя
команды и интеграция в меню могут конфликтовать. Перед сменой способа
сохраните данные и удалите прежний код его штатным способом.

3.1. Tar — только своему пользователю, без sudo

  ./install.sh --user

Код:
  ${XDG_DATA_HOME:-$HOME/.local/share}/zarnitsa-program/releases/<VERSION>-<REVISION>
Ссылки:
  ${XDG_DATA_HOME:-$HOME/.local/share}/zarnitsa-program/current
  ${XDG_DATA_HOME:-$HOME/.local/share}/zarnitsa-program/previous
Стабильная команда:
  $HOME/.local/bin/zarnitsa
Ярлык:
  ${XDG_DATA_HOME:-$HOME/.local/share}/applications/zarnitsa.desktop

Если ~/.local/bin отсутствует в PATH:

  "$HOME/.local/bin/zarnitsa"

User-установка не выдаёт привилегий помощнику. Используется доступный ICMP-путь
или штатный ping; подробности ниже.

3.2. Tar — системная установка

Сначала проверьте доверие к комплекту; только затем:

  sudo ./install.sh --system

Код и ссылки:
  /opt/zarnitsa/releases/<VERSION>-<REVISION>
  /opt/zarnitsa/current
  /opt/zarnitsa/previous
Стабильная команда:
  /usr/local/bin/zarnitsa
Ярлык:
  /usr/local/share/applications/zarnitsa.desktop

Системная установка пробует выдать cap_net_raw только статическому
ICMP-помощнику в защищённом root-owned дереве. Само окно затем запускайте
обычным пользователем. Конфиг интерактивного пользователя остаётся в его HOME.

Установщик проверяет SHA256SUMS до копирования и на копии, не должен
перезаписывать чужие команды/ярлыки и не удаляет старые релизы. Он не ставит
пакеты ОС и не открывает сетевые порты в firewall.

3.3. Отдельный .deb

Используйте ФАКТИЧЕСКОЕ имя полученного файла:

  sudo dpkg -i ./ИМЯ_ПОЛУЧЕННОГО_ПАКЕТА.deb

Код пакета — /opt/zarnitsa-deb, команда — /usr/bin/zarnitsa.
Tar-install/uninstall не управляют этим каталогом. Пакет устанавливается
через dpkg, без apt. Если dpkg сообщил о несовместимости или недостающем
базовом компоненте, не тяните автоматически пакеты из Интернета: проверьте
требования и получите у поставщика подходящий комплект.

Обычная установка сама по себе службу не активирует.


4. ОБНОВЛЕНИЕ, ОТКАТ, УДАЛЕНИЕ
==============================

Перед изменением установки:
  - сохраните конфиг, secrets.json и каталог данных;
  - завершите GUI через «Выход»/Ctrl+Q, а не просто спрячьте в трей;
  - если работает ваша служба, остановите её;
  - распакуйте и проверьте НОВЫЙ комплект отдельно.

Обновление tar — повторите из нового Zarnitsa/ ту же команду:

  ./install.sh --user

или для системной установки:

  sudo ./install.sh --system

Используйте прежнего владельца и те же XDG-пути. Установщик переключает
current на проверенный релиз, предыдущий сохраняется в previous. Уже
работающий процесс не меняет свой бинарник автоматически: запустите заново.
Не редактируйте VERSION/REVISION или SHA256SUMS ради обхода отказа проверки.

Откат tar при наличии отличающегося проверенного previous:

  ./install.sh --user --rollback
  sudo ./install.sh --system --rollback

Эти две строки — альтернативы, не последовательные действия. Откат меняет
выбор кода current/previous, не восстанавливает из резервной копии конфиг
и не гарантирует совместимость формата данных с любой старой версией.

Если исходная распакованная папка уже убрана, пользовательский откат:

  "${XDG_DATA_HOME:-$HOME/.local/share}/zarnitsa-program/current/install.sh" --user --rollback

Системный откат:

  sudo /opt/zarnitsa/current/install.sh --system --rollback

Удаление tar-кода из распакованного комплекта:

  ./uninstall.sh --user
  sudo ./uninstall.sh --system

Либо из установленного релиза:

  "${XDG_DATA_HOME:-$HOME/.local/share}/zarnitsa-program/current/uninstall.sh" --user
  sudo /opt/zarnitsa/current/uninstall.sh --system

Деинсталлятор показывает пути и запрашивает подтверждение. Для заранее
согласованного запуска без вопроса добавьте --yes. Этот флаг не отменяет
проверок принадлежности и целостности файлов. При наличии своей службы
скрипт проверяет её путь, затем останавливает/отключает её.

СОХРАНЯЮТСЯ конфиг, secrets, журналы, внешние --config, /var/lib/zarnitsa/
и учётная запись службы. Изменённый релиз или посторонние файлы могут
остановить безопасное удаление: это не повод заменять его слепым rm -rf.

Обновление .deb — dpkg -i нового пакета. Удаление .deb:

  sudo dpkg -r zarnitsa

Пользовательские данные лежат отдельно от кода. Tar-откат для .deb неприменим;
для возврата на предыдущий .deb нужен сохранённый подходящий пакет и проверка
совместимости данных. Команду purge здесь не используем.

Память процесса не является резервной копией: сырые замеры и графики
исчезают при остановке, даже если файлы конфигурации полностью сохранены.


5. ICMP И ПРАВА ПОМОЩНИКА
========================

В «Настройки → ICMP» доступны:
  auto    — выбор доступного пути: сокет, помощник, системный ping;
  socket  — сокет непосредственно в программе, если разрешён ОС;
  helper  — отдельный zarnitsa-icmp;
  ping    — системный ping, отдельный процесс на замер.

Фактический режим и причину fallback смотрите в окне настроек/диагностике.
Отсутствие ICMP-ответа не доказывает, что компьютер выключен: ICMP может
фильтроваться. Для такой службы выберите TCP/HTTP/SIP по её назначению.

Статический помощник не связан с Qt. Разрешение cap_net_raw+ep допустимо
только для него, после установки в root-owned дерево без права записи
группе/остальным. Переносной и user-каталог для этого не подходят: пользователь
может подменить исполняемый код. Qt-бинарник НЕ должен иметь capabilities,
setuid или setgid. Не запускайте окно от root ради ICMP.

Только диагностика, без изменений:

  ./configure-icmp.sh

Для уже проверенной системной tar-установки:

  sudo /opt/zarnitsa/current/configure-icmp.sh --enable
  sudo /opt/zarnitsa/current/configure-icmp.sh --disable

У .deb соответствующий скрипт находится в /opt/zarnitsa-deb/.
Системная tar-установка сама пробует --enable. Если файловая система,
nosuid/file-capability политика или МКЦ запрещает нужное действие, остаётся
штатный ping с теми правами, которые уже назначены администратором ОС.

Скрипты не меняют sysctl, ping_group_range или firewall и не назначают setuid.
Не выдавайте cap_net_raw Qt-приложению, динамическому загрузчику или shell.
Работа помощника с реальным МКЦ должна быть отдельно проверена организацией.

ICMP IPv6 идёт через системный ping; сокет/помощник текущего быстрого пути
рассчитаны на IPv4. При сотнях целей системный ping создаёт больше процессов;
лимит параллельных ping по умолчанию 64, допустимое значение 1–1024.
Это предел настройки, а не подтверждённая ёмкость рабочего места.


6. HEADLESS И НЕОБЯЗАТЕЛЬНАЯ СЛУЖБА
===================================

Мониторинг без окна и без X:

  ./zarnitsa.sh --headless

В этом режиме API по умолчанию включается на 127.0.0.1:8790.
Вообще без API:

  ./zarnitsa.sh --headless --no-api

Отдельный профиль headless:

  ./zarnitsa.sh --headless --config "$HOME/zarnitsa-service/zarnitsa.json"

Не запускайте одновременно GUI и headless с одним конфигом: оба процесса
могут сохранять его и конкурировать за один API-порт. Остановка ручного
headless — Ctrl+C или штатный SIGTERM.

Обычный install НЕ устанавливает службу. Необязательные варианты:

  ./install.sh --user --service
  sudo ./install.sh --system --service

--service подготавливает unit, но НЕ выполняет enable/start. Системный вариант
также подготавливает служебную учётную запись zarnitsa без обычного входа
и каталог /var/lib/zarnitsa. Конфиг службы отличается от конфига GUI.

Предварительный просмотр unit, без установки:

  ./install.sh --user --print-service
  sudo ./install.sh --system --print-service

User-unit:
  ${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/zarnitsa.service
Системный unit:
  /etc/systemd/system/zarnitsa.service
Конфиг системной службы:
  /var/lib/zarnitsa/zarnitsa.json
Данные системной службы:
  /var/lib/zarnitsa/zarnitsa-data/

Включать только ПОСЛЕ просмотра unit и проверки конфигурации.
Для пользовательской службы, в сессии её владельца:

  systemctl --user daemon-reload
  systemctl --user enable --now zarnitsa.service
  systemctl --user status zarnitsa.service

Остановка/отключение:

  systemctl --user disable --now zarnitsa.service

Для системной службы:

  sudo systemctl daemon-reload
  sudo systemctl enable --now zarnitsa.service
  sudo systemctl status zarnitsa.service

Остановка/отключение:

  sudo systemctl disable --now zarnitsa.service

Не выполняйте обе группы команд без необходимости. User-служба не является
обещанием работы после выхода пользователя: это зависит от user-manager
и политики системы. Автоматически менять эту политику инструкция не требует.

Системный процесс работает от zarnitsa, не от root. NoNewPrivileges=no нужен,
чтобы при exec filecap получил отдельный статический помощник.
CapabilityBoundingSet=CAP_NET_RAW ограничивает потолок возможных прав,
но НЕ выдаёт capability процессу Qt. AmbientCapabilities не задаётся.
Нельзя заменять это AmbientCapabilities=CAP_NET_RAW для всего приложения.

Unit выводит статусы в journal, но НЕ передаёт --print-api-token.
Не добавляйте этот флаг в службу: он явно раскрывает токен в stdout/journal.
После обновления кода свою ранее запущенную службу надо запустить заново.


7. ДОБАВЛЕНИЕ ЦЕЛЕЙ И РАБОТА В ОКНЕ
===================================

Строка добавления понимает:

  127.0.0.1                       ICMP
  10.10.20.10:443                  TCP connect
  tcp:10.10.20.10:22               TCP connect
  https://10.10.20.10/healthz      HTTPS GET
  sip:10.10.20.20                  SIP OPTIONS/UDP, порт 5060
  sip:10.10.20.20:15060            SIP OPTIONS/UDP, иной порт
  dns:localhost                   разрешение имени средствами системы

Подпись после « # »:

  10.10.20.1 # Шлюз учебного сегмента

Для группы и подробных параметров используйте «Новая цель…» (Ctrl+N).
Шаблон H.323 проверяет TCP 1720, не совершает H.323-звонок. Шаблон Инея —
HTTP /login, шаблон Росы — HTTPS /healthz; задайте фактический адрес/порт.

TXT-список, например targets.txt:

  # Учебный сегмент
  127.0.0.1 # Эта машина
  10.10.20.1 # Шлюз
  10.10.20.10:443 # HTTPS-порт

Строка «# Название» задаёт ГРУППУ, это не просто игнорируемый комментарий.
Пустые строки пропускаются.

  ./zarnitsa.sh --list ./targets.txt --group "Из списка"

В окне «Импорт → Из файла…» (Ctrl+I) есть предпросмотр и выбор строк.
В CLI --list добавляет цели напрямую. Поддерживаются TXT, CSV/TSV,
vmPing.xml, собственный JSON и JSON-карточки Инея. CSV поддерживает
разделители «;», запятую или табуляцию; удобно задать заголовки:

  Адрес;Имя;Группа;Тип;Порт;Заметки
  10.10.20.20;Учебный телефон;Сегмент;sip;5060;Проверка стека

JSON-экспорт целей сохраняет больше настроек, чем TXT/CSV. Экспорт целей
не является полной резервной копией приложения: отдельно нужны настройки,
источники, secrets и дисковые журналы. Импорт vmPing не означает перенос
всех возможностей, истории и настроек самого vmPing.

Основные действия:
  Ctrl+N   новая цель              Ctrl+L   фокус на вводе адресов
  Ctrl+F   поиск                   Ctrl+I   импорт файла
  Ctrl+,   настройки               Ctrl+T   трассировка
  F11      экран дежурного          F12      журнал
  Ctrl+Q   настоящий выход из программы

Через меню «Вид»: «Плитки», «Компактно», «Таблица», тёмная/светлая тема,
сортировка и «Только проблемные». В контекстном меню цели — карточка,
изменение, пауза, группа, зависимость от родителя, сброс статистики.
Набор можно сохранить, затем добавить к текущим целям или открыть вместо них.
Замена текущего списка требует осознанного выбора пользователя.

Родительская зависимость помечает дочерние проблемы и подавляет лишние
оповещения о них; она не доказывает физическую топологию сети. Проверки
дочерних целей не следует считать автоматически выключенными.

Уведомления в трее зависят от графической среды. Если трея нет, не прячьте
единственное окно. Реальный Fly tray отдельно не подтверждён. Окошко в углу,
внутреннее сообщение и звук имеют собственные переключатели; звук зависит
от доступного аудиовывода/утилит. Веб-страница открывается внешним браузером.

Встроенные трассировку, поиск узлов подсети и DNS запускайте только
с разрешения на соответствующую сеть. Зарница — мониторинг и диагностика,
не генератор нагрузки; режима flood/DoS нет.

Параметры CLI (подробная справка — раздел 13):
  -i, --interval СЕК      интервал на текущий запуск
  -w, --timeout МС        таймаут на текущий запуск
  --list ФАЙЛ            добавить список
  --group ИМЯ            группа для добавляемых CLI-адресов
  --config ФАЙЛ          отдельный конфиг и каталог данных рядом
  --headless             без окна; --no-api отключает API
  --api АДРЕС:ПОРТ       явно выбрать/включить API
  --theme dark|light     тема
  --density comfortable|compact|list
  --wall                 экран дежурного сразу
  --minimized            старт в трее, если трей доступен
  --no-single            не передавать адреса уже открытому окну
  --demo                 синтетические данные

Обычно второй графический запуск передаёт адреса уже открытому окну.
Не рассчитывайте, что прочие параметры перенастроят старый процесс.
Для независимого экземпляра выбирайте отдельный --config, а не общий файл.


8. НАСТРОЙКИ, ПОКАЗАТЕЛИ, ИСТОРИЯ
=================================

Общие значения «Настройки → Проверки» и границы настроек:

  Параметр                  По умолчанию       Допустимый диапазон
  Интервал                  1 с                0,1–86400 с
  Таймаут                   1000 мс            50–60000 мс
  Размер ICMP               56 байт            0–65000 байт
  TTL                       64                 1–255
  Неудач до down            3                  1–100
  Успехов для выхода down   2                  1–100
  Порог задержки            150 мс             0–60000 мс; 0 — не следить
  Динамический порог        выключен           лучший RTT + прибавка
  Прибавка к лучшему RTT    60 мс              1–60000 мс
  Порог потерь              10 %               0–100 %; 0 — не следить
  Окно потерь/jitter        60 замеров         5–600 замеров
  Дребезг                   6 смен за 600 с    2–100 смен
  Окно дребезга в JSON      600 с              30–86400 с
  Задержка оповещения down  0 с                0–86400 с
  Параллельных ping         64                 1–1024
  Колонки                   0 (авто)           0–32
  Хранение журнала          12 месяцев         1–120 месяцев

В GUI окно дребезга задаётся целыми минутами, 1–1440. У отдельных целей
большинство нулевых значений означает «общее», у потерь это значение -1.
Настройки одной цели могут отличаться от общих. Предел размера пакета —
предел ввода, не гарантия прохождения такого пакета по MTU вашей сети.
Минимальный интервал не означает, что при длинном таймауте каждый замер
фактически завершится с этим периодом. Не включайте короткий интервал
на большом списке без проверки допустимой нагрузки на сеть.

Статусы:
  В норме / up         проверка успешна, пороги качества не нарушены;
  Плохо / degraded     отвечает, но задержка/потери либо сертификат требуют
                       внимания;
  Нет связи / down     серия неудач достигла заданного порога;
  Нет данных / unknown ещё недостаточно результатов;
  Пауза / paused       цель отключена пользователем.

По умолчанию down после трёх неудач подряд, выход из down после двух успехов
подряд. Из unknown первый успешный ответ даёт up сразу. Потери считаются
в окне замеров; проверка задержки сглаживается по последним успешным ответам.
Для HTTPS приближение окончания сертификата (менее 14 дней) тоже влияет
на «Плохо». После восстановления потери в окне могут ещё оставаться высокими.

Что именно измеряет проверка:
  - ICMP: время echo-ответа; заблокированный ICMP не равен выключенному узлу.
  - TCP: установление соединения, не успешный вход и не исправность приложения.
  - HTTP: GET, задержка до заголовков ответа; по умолчанию подходит 2xx/3xx.
    Редирект автоматически не проходится. Можно задать точный статус
    и подстроку в первых 65536 байтах тела, читаемого как UTF-8.
    Для контроля конечной страницы задавайте её URL и нужный статус.
  - HTTPS: обычная проверка доверия или явный pin SHA-256 сертификата.
    Pin — сертификата, не произвольной строки и не отпечатка публичного ключа.
    Безопаснее сверить pin, чем отключать TLS-проверку.
  - SIP: OPTIONS по UDP/IPv4. Подходящий SIP-ответ на запрос, даже 401/403/404,
    означает, что стек ответил. Это не регистрация и не успешный звонок.
  - DNS: системное разрешение имени, с учётом его механизмов/кэшей;
    не отдельный DNS-пакет к выбранному серверу и не проверка DNSSEC.

Jitter — среднее абсолютное изменение RTT между соседними успешными ответами
в выбранном окне. MOS 1–4,5 — упрощённая расчётная оценка по RTT, разбросу
и потерям. Реального RTP, голоса, кодека и односторонней медиазадержки здесь
нет. Нельзя выдавать MOS за сертифицированный тест качества разговора.

История на каждую цель:
  - в памяти 600 последних сырых замеров;
  - в памяти 1440 поминутных агрегатов;
  - на диске журнал смен состояния, НЕ все сырые пакеты.

600 замеров — примерно 10 минут ТОЛЬКО при фактическом периоде 1 с. При другом
периоде временная глубина другая. После рестарта графики/статистика из памяти
исчезают. Дисковый JSONL-журнал сохраняется и не восстанавливает эти графики.

«Доступность за 24 ч» — 100 × успешные / выполненные замеры в имеющихся
поминутных данных за последние сутки. Это НЕ wall-clock SLA: выключенная
программа, паузы и отсутствующие данные не подтверждают доступность за это
время. При пустой статистике нет достоверного процента.

Журнал: F12. Файлы в каталоге данных — events-ГГГГ-ММ.jsonl, технический
zarnitsa.log. JSONL удобен для архивирования; окно/история API ограничены
недавними событиями, а не обязаны показывать весь дисковый архив.
Срок хранения регулируется отдельно; для обязательного архива делайте
резервные копии до штатной очистки старых месяцев.


9. ИМПОРТ И СИНХРОНИЗАЦИЯ ИНЕЯ/РОСЫ
===================================

Обе интеграции необязательны. Зарница не изменяет код, карточки телефонов
и настройки Инея/Росы. Обычный вход/выход создаёт и закрывает сессию на сервере.
Общего входа SSO, федерации, распространения учётных записей нет.

9.1. Иней из файла — без серверного пароля

Через «Импорт → Из файла…» выберите phones_<user>.json или совместимую
выгрузку карточек. Читаются номер, имя, IPv4; некорректные адреса пропускаются
с предупреждением. Такой импорт не является сетевым источником по расписанию.

9.2. Иней по сети

«Импорт → Телефоны из Инея…»:
  - адрес, например http://10.10.20.10:8000;
  - логин и пароль разрешённой учётной записи;
  - целевая группа;
  - ICMP либо SIP OPTIONS/UDP 5060;
  - при необходимости общие наборы;
  - сначала ручная проверка, затем при необходимости расписание.

Сетевой интерфейс: POST /login, GET /phones, опционально GET /shared_sets,
завершение через POST /logout. Обычный HTTP НЕ шифрует пароль и сессию:
используйте только доверенную сеть; при недоверенном канале предпочтите файл
или согласованный защищённый способ доступа.

НЕ ПОВТОРЯЙТЕ неверный пароль: после 7 неудач Иней блокирует адрес на 15 минут.
После ошибки аутентификации автосинхронизация приостанавливается; состояние
паузы сохраняется. Исправьте данные и явно выполните ручную синхронизацию
либо измените настройки источника. Запускать цикл входа для подбора пароля
нельзя. Повторная ручная команда тоже считается попыткой со стороны Инея.

9.3. Роса по HTTPS

«Импорт → Абоненты из Росы…»:
  - адрес, например https://10.10.20.30:18443;
  - администраторская учётная запись Росы;
  - «Проверить сертификат»;
  - независимо сверить SHA-256 с администратором/самим сервером;
  - подтвердить отпечаток, выбрать абонентов, режим проверок и группу.

На сервере с доверенным доступом отпечаток можно получить так:

  openssl x509 -noout -fingerprint -sha256 -in cert.pem

cert.pem здесь — ФАКТИЧЕСКИЙ сертификат сервера Росы. Не доверяйте отпечатку,
полученному только из того же неизвестного соединения. При смене сертификата
сначала выясните причину, а не принимайте новый автоматически.

Используемые маршруты:
  POST   /api/v1/sessions
  GET    /api/v1/admin/sip/status
  GET    /api/v1/admin/h323/status
  DELETE /api/v1/session

SIP-адреса берутся из state.registrations[].peer, H.323 — из peer_ip.
Читаются текущие доступные серверу регистрации/адреса, а не полный справочник
всех когда-либо существовавших абонентов. Возможны цели самого сервера:
HTTPS /healthz и SIP. Режим «проверять службу» использует для SIP его порт,
для H.323 — TCP 1720, но реальных звонков не совершает.

9.4. Дальнейшая синхронизация

«Импорт → Источники…» — изменить, «Обновить сейчас», удалить источник.
Расписание: 0 — только вручную, 1–10080 минут — периодические загрузки;
для расписания нужен сохранённый пароль. Не включайте расписание до
успешного ручного входа и не уменьшайте период без необходимости.

Новые цели добавляются, известные обновляются по ключу источника.
Исчезнувшие ПОМЕЧАЮТСЯ «нет в источнике», а не удаляются. Пороговые значения
и ручные заметки сохраняются; имя, адрес, тип, порт и TLS-pin могут обновиться
из источника. Не считайте ручную правку этих полей постоянной при расписании.

При удалении источника можно оставить цели обычными либо явно удалить
вместе с ним. Не удаляйте карточки только из-за кратковременного сбоя импорта.

«Запомнить пароль» необязательно. При выборе пароль записывается рядом
с конфигом в secrets.json с правами 0600, но НЕ ЗАШИФРОВАН. Подробности ниже.


10. КОНФИГ, ПАРОЛИ, РЕЗЕРВНАЯ КОПИЯ
===================================

Обычные пути (учитываются XDG_CONFIG_HOME и XDG_DATA_HOME):
  ~/.config/zarnitsa/zarnitsa.json  — настройки, цели, источники, API-токен;
  ~/.config/zarnitsa/secrets.json  — только запомненные пароли источников;
  ~/.local/share/zarnitsa/         — события и технические журналы.

При --config /path/z.json:
  /path/z.json                    — конфиг;
  /path/secrets.json              — запомненные пароли;
  /path/zarnitsa-data/             — данные и журналы.

У двух конфигов в одном каталоге будут общие имена secrets.json
и zarnitsa-data. Для независимых профилей выбирайте РАЗНЫЕ каталоги.

Автоматический переносной режим ищет уже существующий zarnitsa.json
в каталоге исполняемого файла: Zarnitsa/bin/zarnitsa.json.
Файл Zarnitsa/zarnitsa.json рядом с корневым launcher сам по себе для этого
не подходит. Рекомендуется явный --config ВНЕ установленного/проверяемого
дерева: добавленные туда данные нарушают проверку состава и мешают удалению.

Конфиг и secrets сохраняются с правами 0600. Это права доступа, не шифрование.
На FAT/exFAT и иных ФС без POSIX-прав нельзя полагаться на эту защиту.
TLS-ключ и резервные копии тоже требуют защиты. Не храните секреты
в HTTP URL, TXT-списках, истории shell, общих каталогах или диагностических
пакетах для публичной отправки.

Резервная копия:
  1) Завершите процесс, использующий профиль.
  2) Скопируйте zarnitsa.json и, если есть, secrets.json в защищённое место.
  3) Скопируйте весь каталог данных и используемые TLS-ключ/сертификат.
  4) Сохраните фактические пути и проверьте возможность чтения копии.
  5) Восстанавливайте в пустой отдельный профиль, проверяя владельца/права.

Экспорт JSON целей не заменяет эту копию. Ни копия конфига, ни архив JSONL
не сохраняют кольцо RTT-замеров из памяти. Удаление кода приложения не должно
быть способом удаления чувствительных данных: у них отдельный жизненный цикл.


11. API, ТОКЕН И TLS
====================

11.1. Включение и авторизация

В GUI API по умолчанию выключен; включается в «Настройки → API».
Headless включает его, кроме случая --no-api. Адрес по умолчанию:

  http://127.0.0.1:8790

Это loopback: доступ с другого компьютера к нему не предусмотрен.
Для явного запуска:

  ./zarnitsa.sh --headless --api 127.0.0.1:8790

API-токен генерируется локально, хранится в settings.api_token конфига 0600.
В GUI есть копирование/замена токена. По умолчанию headless НЕ печатает
сам токен. Флаг --print-api-token явно разрешает его вывод в stdout;
не используйте его в службе, автоматизации с общим логом и journal.
Не запускайте вторую копию с тем же конфигом только ради печати токена.

Для всех маршрутов, кроме /healthz, нужен заголовок:

  Authorization: Bearer <ТОКЕН>

НЕ передавайте токен в URL, query string, имени файла или JSON-комментарии.
В API нет отдельных ролей: владелец токена может добавлять/удалять цели.
Даже loopback-токен не публикуйте другим пользователям машины.

11.2. Маршруты

  GET    /healthz                 публичный статус процесса/API;
  GET    /api/v1/targets          цели, фильтры group и status;
  POST   /api/v1/targets          добавить одну цель или массив;
  GET    /api/v1/targets/<id>     подробности цели, недавние замеры/события;
  DELETE /api/v1/targets/<id>     удалить цель;
  GET    /api/v1/summary          сводка состояний и режим ICMP;
  GET    /api/v1/history          события, фильтры since, limit, id;
  GET    /api/v1/events           SSE-поток событий;
  GET    /api/v1/availability     компактный отчёт в похожей на Иней форме;
  GET    /metrics                 метрики Prometheus, тоже с Bearer.

since — Unix-время в миллисекундах. limit по умолчанию 200, максимум 5000.
History — журнал событий, НЕ API всех сырых RTT-измерений за месяцы.
SSE — текущий поток, не обещание надёжной очереди и полного повтора пропусков.
POST принимает не более 5000 объектов за один запрос; это не оценка
подтверждённой ёмкости мониторинга. Полный редактор всех настроек через API
не заявлен: для них есть карточка цели и конфиг.

Пример ОДНОСТРОЧНОГО тела POST /api/v1/targets:

  {"line":"127.0.0.1","name":"Локальная проверка","group":"Проверка API"}

Нужен Content-Type: application/json. Успешный POST возвращает 201 и объект
с id (для массива — массив). Удаление цели возвращает 204.

Форма availability:
  {"revision":...,"results":[[id,"green|yellow|red|gray",RTT_мс_или_null,возраст_мс_или_null],...]}

Это GET-отчёт, а не регистрация узла в «Виктории», не полноценная федерация
Инея и не перенос её функций. /healthz=ok не означает, что все цели исправны.
Метрики могут содержать адреса и имена целей — не открывайте их всему миру.

11.3. Примеры клиента без токена в истории команд и аргументах curl

curl нужен только для этих примеров, не для работы самой Зарницы.
Если его нет на изолированной машине, используйте заранее подготовленный
разрешённый API-клиент; инструкция не требует установки через Интернет.

В Bash вручную прочитайте токен в НЕэкспортируемую переменную:

  read -r -s -p 'Токен API: ' ZARNITSA_API_TOKEN
  printf '\n'

Заголовок передаётся curl через stdin, а не через URL или его аргумент:

  printf 'header = "Authorization: Bearer %s"\n' "$ZARNITSA_API_TOKEN" | curl --config - --fail --silent --show-error http://127.0.0.1:8790/api/v1/summary

Добавление локальной цели (меняет список наблюдения):

  printf 'header = "Authorization: Bearer %s"\n' "$ZARNITSA_API_TOKEN" | curl --config - --fail --silent --show-error -H 'Content-Type: application/json' --data '{"line":"127.0.0.1","name":"Локальная проверка","group":"Проверка API"}' http://127.0.0.1:8790/api/v1/targets

Поток SSE, завершение — Ctrl+C:

  printf 'header = "Authorization: Bearer %s"\n' "$ZARNITSA_API_TOKEN" | curl --config - --no-buffer http://127.0.0.1:8790/api/v1/events

После работы:

  unset ZARNITSA_API_TOKEN

Используйте токен, созданный приложением; не вводите произвольный текст
с переводами строк/кавычками в пример curl-config. Не включайте set -x
и подробное журналирование секретов. Терминал должен быть доверенным.

11.4. TLS для доступа вне loopback

При адресе вне loopback без сертификата/ключа API отказывается стартовать.
Не обходите это правило внешней публикацией незащищённого порта.
Создание локальной самоподписанной пары, например для учебного адреса:

  ./make-cert.sh --dir "$HOME/.config/zarnitsa/tls" --ip 10.10.20.10 --ip 127.0.0.1 --dns localhost

Нужен минимум один SAN --ip/--dns; флаги можно повторять. Внешние IP
автоматически не добавляются. --days по умолчанию 365, диапазон 1–3650.
Создаются zarnitsa.key (0600) и zarnitsa.crt; существующая пара заменяется
только после подтверждения либо явного --yes. Используется системный openssl
или проверенный runtime/bin/openssl. Скрипт не обращается в сеть, не включает
API и не изменяет конфиг/firewall.

В «Настройки → API» задайте фактический адрес, путь сертификата и ключа.
При ручном редактировании сохраните все остальные поля конфига.
Пример ТОЛЬКО полей внутри settings, а не замена всего файла:

  "api_enabled": true,
  "api_listen": "10.10.20.10:8790",
  "api_tls_cert": "/home/operator/.config/zarnitsa/tls/zarnitsa.crt",
  "api_tls_key": "/home/operator/.config/zarnitsa/tls/zarnitsa.key"

/home/operator — пример; укажите свои абсолютные пути. JSON не разворачивает
$HOME и ~ в этих полях. Не стирайте уже созданный settings.api_token.
Для системной службы ключи должны быть доступны пользователю zarnitsa
в разрешённом ей каталоге, например /var/lib/zarnitsa/tls/, не в HOME
оператора, закрытом ProtectHome. Приватный ключ не выдавайте другим.

Клиент должен явно доверять сертификату и проверять имя/IP. Для curl
используйте --cacert с проверенным сертификатом, а не -k/--insecure.
Самоподписанный сертификат не становится доверенным от самого факта создания.
Разрешение сетевого доступа — отдельное решение администратора; скрипты
не открывают firewall и не отключают защиту.


12. КОМАНДЫ ОПОВЕЩЕНИЯ И ВЕБХУК
===============================

В «Настройки → Оповещения» независимо выбираются трей, сообщения в окне,
угловое окно, звук, восстановление, «Плохо», тишина при дребезге и отсрочка
сообщения о down. Дочерняя проблема за лежащим родителем не должна создавать
такую же лавину самостоятельных оповещений.

Внешняя команда выполняется с правами процесса Зарницы. Команду, исполняемый
файл и настройки выбирает доверенный пользователь, а не импортируемая цель.
По умолчанию поле команды пусто, shell-режим выключен.

Обычный режим, БЕЗ shell:
  сначала доверенный шаблон разбирается на программу и аргументы,
  затем значения подставляются ВНУТРИ уже выделенных аргументов.

Например, только если такой доверенный обработчик действительно установлен:

  /usr/local/bin/zarnitsa-notify "{status}" "{name}" "{address}"

Поддерживаемые подстановки:
  {name} {address} {group} {status} {status_title} {prev}
  {rtt} {loss} {reason} {text} {time}

Не выбирайте исполняемый файл по имени цели и не заворачивайте эту схему
самостоятельно в sh -c с подстановками: так можно вернуть интерпретацию
недоверенных данных как кода.

При включении «через /bin/sh -c» всё поле — БУКВАЛЬНЫЙ доверенный скрипт.
Подстановок {name}, {text} и других фигурных шаблонов в этом режиме НЕТ.
Данные берите только из окружения, обязательно заключая значения в кавычки:

  printf '%s\n' "$ZARNITSA_TEXT" >> "$HOME/zarnitsa-alerts.log"

Переменные события:
  ZARNITSA_NAME, ZARNITSA_ADDRESS, ZARNITSA_GROUP, ZARNITSA_STATUS,
  ZARNITSA_PREV, ZARNITSA_TEXT, ZARNITSA_RTT, ZARNITSA_LOSS,
  ZARNITSA_REASON, ZARNITSA_TIME.

Нельзя использовать eval и повторно исполнять содержимое этих переменных.
Перед включением обработчика проверьте его локально; вывод команды не должен
содержать пароли или токены. Отсутствие окна у headless не повышает доверие
к его конфигу.

Вебхук по умолчанию НЕ задан. После настройки Зарница посылает JSON-события
на выбранный URL; ошибки доставки могут приводить к повторной отправке.
Не настраивайте внешний вебхук, почту или иной внешний сервис без решения
пользователя о передаче названий, адресов и событий локальной сети.
Сам опрос целей и подключение к выбранным источникам остаются сетевыми
действиями, даже если Интернет для установки не нужен.


13. ДИАГНОСТИКА И ТИПИЧНЫЕ НЕПОЛАДКИ
====================================

Все команды диагностики — только для уже ДОВЕРЕННОГО комплекта.
Без изменения конфигов/прав и без сетевых проб:

  ./check-runtime.sh
  ./check-runtime.sh --qt-runtime system
  ./check-runtime.sh --qt-runtime bundled
  ./check-runtime.sh --headless
  ./check-runtime.sh --offscreen
  ./configure-icmp.sh
  ./diagnose.sh
  ./diagnose.sh --headless --output "$HOME/zarnitsa-diagnose.txt"

diagnose не читает содержимое конфигов, secrets и журналов, не печатает
пароли/токены и не опрашивает сеть. В отчёте остаются ОС, версия, пути,
зависимости и права. Существующий --output не перезаписывается: выберите
новое имя. Файл отчёта храните ВНЕ дерева комплекта, иначе он станет
посторонним файлом при проверке SHA256SUMS/удалении.

Проблема: нет подходящего Qt или «could not load xcb».
  Сравните system/bundled в check-runtime. Проверьте DISPLAY и обычную
  сессию пользователя. Не копируйте одну случайную libQt5*.so поверх другой
  и не смешивайте Qt-плагины. Headless проверяйте с --headless, без X.
  Для отсутствующих базовых библиотек нужен совместимый комплект/образ ОС,
  а не автоматический apt из внешней сети.

Проблема: Permission denied при запуске с USB.
  Проверьте права и noexec. Скопируйте весь комплект на разрешённую ФС.
  Не назначайте setuid и не запускайте GUI через sudo.

Проблема: TCP/HTTP работают, ICMP — нет.
  Посмотрите фактический ICMP-режим и configure-icmp без флагов.
  Штатный ping может быть недоступен пользователю или закрыт политикой.
  Нужна проверка администратора; не меняйте sysctl/firewall вслепую.

Проблема: системный install отказал из-за прав/чужого файла.
  Не подменяйте команду, не удаляйте чужой ярлык и не делайте chmod 777.
  Проверьте область установки, старый способ tar/.deb, владельца и состав.
  Если осталась блокировка .install.lock, сначала убедитесь, что установка
  или удаление больше не выполняется; не снимайте её во время операции.

Проблема: проверка SHA256SUMS перестала проходить.
  Данные, отчёты и дополнительные файлы не должны появляться в релизе.
  При изменении бинарников, библиотек или подписи старый манифест больше
  не соответствует файлам. Получите проверенный комплект; не обходите
  контроль простым пересчётом сумм неизвестных файлов.

Проблема: API не слушает.
  В GUI он по умолчанию выключен. Проверьте адрес/порт, отсутствие второго
  экземпляра, сохранённый токен и читаемость PEM. Вне loopback нужен TLS.
  Headless при неудаче API может продолжать мониторинг: проверяйте сообщение
  о запуске и /healthz, а не только наличие процесса.

Проблема: Иней не принимает пароль.
  Остановитесь, проверьте учётные данные. После 7 ошибок блокировка 15 минут.
  Не пытайтесь лечить вход частыми повторами и расписанием.

Проблема: Роса показывает другой сертификат.
  Независимо проверьте смену сертификата у администратора. Не отключайте
  TLS-проверку, чтобы убрать сообщение. При переиздании нужен новый pin.

Проблема: после перезапуска пустой график.
  Это ожидаемо: замеры и поминутные агрегаты находятся в памяти. Дисковый
  журнал хранит события, не всю последовательность RTT.

Проблема: программа пропала после закрытия окна.
  Возможно, включено закрытие/сворачивание в трей. Настройки трея зависят
  от рабочей среды; настоящий Fly tray отдельно не подтверждён.

Справка launcher и скриптов:

  ./zarnitsa.sh --help
  ./install.sh --help
  ./uninstall.sh --help
  ./configure-icmp.sh --help
  ./check-runtime.sh --help
  ./diagnose.sh --help
  ./make-cert.sh --help

--help launcher — краткая справка оболочки. Полная справка приложения:

  ./bin/zarnitsa --headless --help

Если для прямого запуска не настроены библиотеки, в доверенном комплекте
можно явно подключить его runtime (из корня Zarnitsa/):

  env -u LD_PRELOAD -u LD_AUDIT LD_LIBRARY_PATH="$PWD/runtime/lib" ./bin/zarnitsa --headless --help

Это только просмотр CLI, не проверка рабочего мониторинга. Для обычной
работы используйте launcher и его выбор runtime, а не прямой bin/zarnitsa.
